# Focusory 功能设计

把需求整理成用户可确认、开发者可实现、测试人员可验证的设计基线。文档应回答：为什么做、做什么、使用什么数据、谁负责什么、失败怎么办、如何证明完成。

保持文档精简。引用已有 UC、BR、架构和接口规范，不重复抄写；只展开本功能特有的语义、决策和边界。设计没有就绪前不要编码，也不要把推断写成既定规则。人工审核结果必须保存在功能文档头部；AI 不得自行填写「已通过」。

## 事实优先级

1. 用户当前明确确认的要求。
2. 用户指定的规则与根目录 `AGENTS.md`。
3. 已确认的产品、架构、接口和数据文档。
4. 现有代码与测试反映的实现现状。
5. 为补齐设计作出的推断。

冲突时不自行折中。记录冲突、影响和推荐方案；会改变用户行为、数据语义、接口或范围的问题列为待决策项。只询问无法从现有基线确认且会实质改变设计的问题。

## 建立上下文

1. 阅读 `AGENTS.md`。
2. 按功能范围检查：
   - `文档/产品/01-产品需求.md`
   - `文档/产品/02-用户故事.md`
   - `文档/产品/功能/README.md` 及对应功能文档
   - `文档/产品/03-逻辑视图.md`
   - 相关交互/UI 规范、开发/过程/物理视图、API 约定和数据模型
3. 阅读相关代码和测试，只用于确认现状、约束与可行性；除非用户另行要求，不修改生产代码。
4. 判断是扩展现有功能、新增能力、修正设计还是纯实现。纯实现使用 `focusory-feature-dev`，实现后追踪同步使用 `focusory-doc-sync`，代码审查使用 `focusory-review`。
5. 创建或重写功能文档前，完整阅读 [`references/feature-document-template.md`](references/feature-document-template.md)。

## 设计内容

功能文档只保留六个一级章节：

1. **目标与范围**：用户问题、功能作用、范围内、非目标、成功结果、关联 UC/BR。
2. **数据与状态**：使用的模型、字段语义、来源、所有者、持久化、同步、生命周期、派生关系和状态变化。
3. **流程与异常**：角色、前置条件、主流程、失败、取消和恢复；使用一张完整 Mermaid 泳道图表达用户、前端、后端及必要的本地存储/外部系统职责。某端不参与时明确写出原因，不虚构调用。
4. **协作约束与实现位置**：按根目录 `AGENTS.md` 的「边界与接口的写法」，只补充泳道图难以表达的本功能特有约束、前后端接口引用及必要实现导航。不重复职责表、内部接口表或其他功能的内部流程；已有规则和通用架构契约用链接引用。
5. **测试场景、验收与异常统计**：编码前可执行的测试场景清单、可观察验收标准、测试层级与建议位置，以及需要记录的失败类型、稳定错误码、日志、指标和告警；不需要远程统计时明确说明。
6. **决策与就绪结论**：只记录本功能新增的已决策项、待决策项、需要同步的权威文档、依赖/风险和能否进入任务拆分；「类型」列只写 `已决策` 或 `待决策`。

文档主标题不编号。六个一级章节依次使用 `## 1. 标题` 至 `## 6. 标题`；二级章节使用 `### 1.1 标题`、`### 1.2 标题`，并在所属一级章节内连续编号。表格标题、Mermaid 内容和更细的说明项不强制编号。

页面、模块和文件位置放在“协作约束与实现位置”中，只保留必要导航与已知实现缺口，不再单独建立交付矩阵。IBM 4+1 只列实际需要同步的文档，不生成全量“是否影响”表。风险、发布、回滚和迁移仅在确有影响时记录。

## 关键设计要求

- 数据部分必须能回答：需要哪些模型、由谁创建和拥有、保存在哪里、何时删除、是否同步、哪些是派生值或 UI 临时状态。
- 状态复杂、存在终态或历史保护时，给出状态表或 Mermaid 状态图；简单状态用文字即可。
- 泳道图必须覆盖触发、校验、数据变化、成功反馈、关键失败和恢复路径，跨泳道箭头与接口或事件一致。
- 删除、不可逆操作和历史数据必须说明确认、保留与恢复边界。
- 本地优先功能必须说明断网、重试、幂等、冲突和本地/云端真值关系。
- 用户可见文案归 String Catalog；Domain 不保存显示文案。
- 内部接口定义和技术隔离要求引用开发视图与代码，不在功能文档逐层列类名、参数和返回值；前后端契约统一维护在 API 约定中。新增或变更契约仍须同步权威文档和测试，不能以精简文档为由省略必要约束。
- UI 设计覆盖实际受影响的初始、空、加载、成功、错误、禁用、离线、冲突、键盘和无障碍状态；不为不相关状态制造内容。
- 测试场景清单使用稳定编号，每个场景至少说明类型、关联 UC/BR/验收项、前置条件与必要数据、操作、可观察预期结果、测试层级与建议位置，以及自动化或人工检查结论。
- 场景覆盖功能实际相关的成功、失败、边界、取消、恢复、离线、并发、幂等和历史保护，不为不相关类别制造场景。每条验收标准与场景编号双向追踪。
- 可自动化的场景在任务完成前落到适当的自动化测试；不适合自动化的纯视觉或真实系统集成场景，写明人工测试步骤、预期结果和不自动化原因。功能设计不强制生产代码前先写或运行失败测试。
- 无法唯一写出预期结果、无法选择合理测试层级，或场景与权威规则冲突时，将其列为待决策项并请人工确认，不得为了使测试可写而自行补充产品规则。
- “异常统计”指错误观测，不重复异常流程：记录必要的错误码、失败次数、重试/队列状态和性能信号，同时避免任务正文、凭据和敏感 payload 进入日志。

保持 Focusory 安静、轻量、可靠。MVP 优先保证计时、任务聚焦、会话记录和基础统计；AI 能力不得打断专注过程。

## 文档落稿与权威同步

用户未要求只讨论时，在关键决策已确认后创建或更新 `文档/产品/功能/Fxx-名称.md`，并按模板填写。功能文档是设计入口，不替代权威规范：

- 行为、UC、BR、失败流程或优先级变化：先更新 `文档/产品/02-用户故事.md`。
- 功能归属或状态变化：更新 `文档/产品/功能/README.md`。
- 核心对象、关系、状态或不变条件变化：更新 `文档/产品/03-逻辑视图.md`。
- 职责、依赖、并发或部署变化：更新对应开发、过程或物理视图。
- API 或持久化语义变化：更新 `文档/架构/05-API约定.md`、`06-数据模型.md` 或迁移说明。
- 交互或视觉基线变化：更新原型交互说明或 UI 规范。
- 关键架构取舍变化：更新决策记录。

没有变化的权威文档不做形式性修改。功能文档引用 `02-用户故事.md` 中的编号规则，不复制完整定义。

## 设计就绪

只有以下问题都有明确答案，且人工审核状态为「已通过」、审核范围覆盖当前可拆分范围，才标记为“可进入任务拆分”：

- 目标、非目标、功能归属和优先级是否确定？
- 数据来源、所有权、状态、持久化、删除和同步是否明确且不矛盾？
- 泳道图是否覆盖成功、失败、取消和恢复，并与接口边界一致？
- 泳道职责、特有协作约束及引用的架构/API 契约是否足以实现，错误与一致性要求是否仍可追踪？
- 测试场景是否已明确前置数据、操作、预期结果、层级和自动化结论，并与验收标准双向追踪？
- 可自动化和需要人工检查的场景是否分类明确，人工场景是否已写明可执行步骤，异常是否可诊断？
- 是否仍有会改变用户行为、数据或接口的待决策项？

待决策项只阻塞部分交付时，明确写出可先拆分的范围和被阻塞的范围。

功能文档发生影响用户行为、数据语义、接口契约或验收预期的实质修改时，将人工审核状态恢复为「未审核」，清空审核日期，并写明需要重新审核的范围和新基线。

## 任务拆分

只有用户明确要求、相应范围已经设计就绪且人工审核记录有效时，才生成开发任务卡。每张卡必须包含任务卡生成 AI、当前开发执行者、目标、非目标、前置阅读/任务、影响模块、接口约束、实现步骤、本卡覆盖的已审核测试场景编号及验收标准、验证命令、停止条件和完成报告格式。开发任务可以交给任意 AI，但不得让开发 AI 自行补充产品决策。

## 验证

落稿后检查：

- 功能索引、UC/BR、状态名、字段名和交叉链接一致。
- 六个一级章节齐全且编号为 `1.` 至 `6.`；二级章节编号与所属一级章节一致并连续；不适用内容有简短理由。
- 每个必要模型都有来源、所有者、生命周期和同步结论。
- 泳道动作位于正确责任方，异常分支落到反馈、数据结果和恢复方式。
- 职责由泳道图表达且不重复列内部接口表；特有约束、前后端接口引用与实现导航可追踪到架构、API、数据模型或代码。不直接调用后端时已说明协作归属。
- 每条验收标准都可追踪到至少一个测试场景，每个场景都有层级、建议位置和自动化结论；异常统计不记录敏感内容。
- 功能文档头部的人工审核状态、日期、范围和基线齐全，且与当前文档内容一致。

运行 `git diff --check`。仅修改设计文档时不要求应用构建，但要报告未自动验证的产品判断。
