- 后续影响：根目录 `AGENTS.md` 增加 AI 协作分工；AI 开发流程增加设计、任务交付、本地实现和云端验收阶段；`opencode.json` 固定本地开发模型。后续任务必须先由 ChatGPT/Codex 明确任务卡，再由 OpenCode 实现。

## 2026-10-13 AI 开发设置人工审核关卡与全程逻辑异常中断

- 背景：既有流程已区分 ChatGPT/Codex 设计审查和 OpenCode 实现，但没有明确功能文档在进入开发前必须经过人工审核，也没有覆盖「设计阶段未发现问题，实现或测试才暴露逻辑异常」的全程中断机制。
- 决策：AI 生成或修改的功能文档在人工审核通过前只是设计草案，不得标记设计就绪、创建正式开发任务或开始编码。审核结果在功能文档头部持久记录审核状态、日期、范围和基线；影响用户行为、数据语义、接口契约或验收预期的实质修改使原审核失效并触发重新审核。人工负责最终功能和表现验收，验收通过不等于合并授权。任何 AI 在任何阶段发现需求或规则歧义、冲突、缺失、产品偏离规则文件，或实现、测试与审查反例证明已审核设计存在逻辑异常时，必须停止受影响工作并请人类开发者确认；人工确认后先更新权威规则、设计文档和任务卡，再恢复实现和回归验证。
- 备选方案：将 Codex 审查视为设计和实现的最终批准；只在设计阶段询问人工；允许 AI 在实现或测试阶段按最容易实现的方案补齐未定义规则。
- 原因：设计审核只能基于当时可见证据，实现、边界测试和真实交互会暴露新的矛盾与反例。由人工保留产品意图、规则变更和最终体验的决策权，可防止 AI 为了完成任务而隐式改变产品、削弱验收标准或让测试迎合错误实现。
- 后续影响：根目录 `AGENTS.md` 增加人工设计审核、最终验收和全程中断规则；`01-AI开发流程.md` 增加固定人工关卡、动态中断条件、中断报告与恢复流程；新任务卡必须写明停止条件。

## 2026-10-13 功能设计采用测试场景清单

- 背景：只在实现后根据代码补充测试，容易让测试迎合已完成实现，也无法及时暴露需求、边界与状态设计中的逻辑缺口。
- 决策：功能文档在人工设计审核前必须提供带稳定编号的测试场景清单，明确前置数据、操作、可观察预期结果、测试层级、建议位置和自动化结论，并与验收标准双向追踪。开发 AI 根据已审核场景实现代码与测试，任务完成前运行适用验证，不强制在生产代码前先编写或运行失败测试。
- 备选方案：不编写设计阶段测试场景，实现完成后再由 AI 自由补充测试；只在任务卡中编写测试计划而不进入功能设计审核；强制所有任务在开发前先执行失败测试。
- 原因：设计阶段固定场景与预期结果，已能够帮助人工发现逻辑缺口，并减少 AI 将已有实现误当产品意图的风险。强制在开发前先执行注定失败的测试增加流程成本，对不同类型改动的价值不稳定，因此不设为统一强制步骤。
- 后续影响：功能文档模板、任务卡模板、AI 开发流程和 Focusory 设计、开发、审查技能增加测试场景追踪要求；既有功能文档在进入新一轮实质设计或任务拆分前补齐对应场景，不做无关批量改写。

## 2026-07-30 数量达标自动完成并允许追加

> 历史决策：其中待办达标与追加仍有效；旧的计划模式规则已被 2026-08-26 原型基线决策取代。

- 背景：达到预估番茄数时，大多数任务可以顺畅结束，但实际工作也可能尚未完成，需要继续追加。
- 决策：待办模式达到目标数量后自动完成，追加番茄钟后恢复为进行中，再次达到新目标时再次自动完成。计划模式当天达到有效目标后自动完成今日目标，当天追加后恢复进行中，且不影响未来日期。用户手动完成的结果不可追加或恢复。
- 备选方案：达到数量后等待用户确认；允许显示超额完成；达到数量后最终完成且不允许继续。
- 原因：自动完成减少常规操作，追加机制覆盖预估不足的情况；通过增加目标而不是显示超额完成，界面仍聚焦实际目标。
- 后续影响：数据模型需要区分系统自动完成和用户手动完成，并保留初始目标、追加数量和最终目标；客户端需要提供“追加 1 个番茄钟”和修改追加数量的入口。

## 2026-07-30 区分删除任务和放弃任务

> 历史决策：删除与放弃的基本原则仍有效；旧的计划每日记录命名已由当前 TaskDailyProgress 契约取代。

- 背景：用户需要清理误创建任务，也可能决定停止已经投入过时间的任务。直接删除已有记录的任务会破坏专注历史和统计。
- 决策：无专注会话和计划每日记录的活动任务允许删除；已有历史记录的活动任务只能放弃。放弃保留历史数据并进入已放弃状态，不允许恢复。
- 备选方案：所有任务都可级联删除；只提供归档；只提供放弃而不提供删除。
- 原因：既满足清理误创建任务的需求，又保证真实专注记录和统计不被破坏。
- 后续影响：任务增加已放弃状态、放弃时间和删除同步标记；客户端需要区分“放弃本次专注”和“放弃任务”，计划放弃后需要停止生成未来每日记录。

## 2026-08-03 本地开发 MySQL 使用官方 9.7.1 容器

- 背景：Python 后端需要一个可立即连接的本地 MySQL 服务，但当前尚未确定业务框架、数据库名称和迁移方案。
- 决策：使用官方 `mysql:9.7.1` 多架构镜像，通过 Compose 启动；端口只绑定 `127.0.0.1:3306`，数据保存到 Docker 命名卷，不映射宿主机目录。当前只创建空的 `focusory` 数据库，不创建业务表，也不配置自动初始化 SQL。
- 备选方案：安装宿主机 MySQL；使用 MySQL 8.4 LTS；使用无持久化容器层；创建数据库并提前执行建表脚本。
- 原因：9.7.1 是当前稳定版本且提供原生 arm64 镜像；容器隔离便于启动和清理；命名卷兼顾数据持久性和不污染工作区；先创建数据库便于后端连接，延后建表避免在业务后端架构未确定前固化 schema。
- 后续影响：本地连接地址固定为 `127.0.0.1:3306`；root 密码仅保存在被 Git 忽略的本地 `.env`；未来业务后端需要新增专用数据库用户和迁移工具，生产环境不得复用本地 root 凭据。

## 2026-08-31 Python 业务后端技术栈

- 背景：Focusory 需要为 macOS 客户端提供账户、任务、会话、统计和幂等同步 API，并使用 MySQL 保存云端数据。后端包尚未创建，需要先固定运行时、Web 框架、持久化、迁移、测试和依赖策略。
- 决策：使用 CPython 3.12.10 标准构建、`uv`、FastAPI、Uvicorn、Pydantic 2、`pydantic-settings`、SQLAlchemy 2 同步 `Session`、PyMySQL、Alembic、HTTPX、pytest/pytest-cov、Ruff 和 mypy。MySQL 目标兼容 9.7 LTS，使用 InnoDB 与 `utf8mb4`。交付使用 Docker，精确 Python 依赖由提交到仓库的 `uv.lock` 锁定。Python 运行时基线于 2026-09-26 从原选定版本修订为 3.12.10，其余技术选型不变。
- 备选方案：Django + Django ORM；Flask + SQLAlchemy；FastAPI + SQLAlchemy `AsyncSession` + 异步 MySQL 驱动；Poetry/pip-tools 依赖管理。
- 原因：FastAPI/Pydantic 可以用类型化 DTO 实现清晰的 `/v1` 契约；SQLAlchemy/Alembic 与 MySQL 的映射、事务和迁移生态成熟。当前规模优先保证用例事务和幂等的可理解性，同步数据库栈比异步栈更少隐式边界；`uv.lock` 保证开发、CI 和生产版本一致。
- 后续影响：创建 `Focusory/backend/` 时必须按开发视图分层，不得将 FastAPI、SQLAlchemy 或 PyMySQL 导入领域层；业务表只通过 Alembic 迁移。首版不引入 Redis、Celery 或消息队列；只有测量证明同步数据库访问成为瓶颈后，才单独评估整体迁移到异步栈。

## 2026-08-31 一个 Focusory 账户可绑定 Apple 和微信

- 背景：原 UserAccount 直接保存单一 `login_provider + provider_user_id`，无法让用户通过 Apple 和微信访问同一份 Focusory 数据。
- 决策：将稳定的 UserAccount 与 AccountIdentity 分离。一个账户可同时具有一条 Apple 和一条微信身份；「provider + provider user ID」全局唯一，「user ID + provider」唯一。绑定必须由已登录账户发起并重新验证目标身份；允许解绑其中一个，但不允许解绑最后一个登录身份。
- 备选方案：在 UserAccount 中固定放置 `apple_user_id` 和 `wechat_user_id`；按邮箱自动合并账户；为每种登录方式创建独立 Focusory 账户。
- 原因：独立 AccountIdentity 可以明确表达一对多绑定和唯一性，并避免将可变第三方属性当作数据所有权。邮箱和昵称不能安全证明两个身份属于同一人，因此不自动合并。
- 后续影响：MySQL 新增 `account_identities`，从 `user_accounts` 移除 provider 字段；`GET /v1/me` 返回已绑定 provider，新增绑定/解绑 API 和 UC-14。客户端需增加账户设置状态与对应测试；已被两个独立 Focusory 账户占用的 Apple/微信身份不在本次自动合并，未来如需合并必须建立独立用例和数据冲突策略。

## 2026-10-12 任务卡片操作不依赖悬停

- 背景：原型把开始专注、完成任务、编辑和删除/放弃放在「鼠标悬停时显示」的操作区里，但 NFR-A11Y-01 要求关键操作不依赖悬停或颜色，只靠键盘或 VoiceOver 也能完成；同时条件渲染会让操作在可访问性树中完全消失，UI 测试也无法用稳定标识驱动。
- 决策：任务卡片的操作常驻显示，悬停和选中只改变边框、背景等视觉强调；操作区保留稳定的 `accessibilityIdentifier`，禁用的开始专注按钮附加 `accessibilityHint` 说明原因。
- 备选方案：保留仅悬停可见并在悬停时临时插入操作；用透明但可点击的按钮占位；增加仅在键盘聚焦时显示的第三套状态。
- 原因：常显同时满足可访问性验收标准、旁白可达性和自动化测试可验证性，不引入两套以上的显示状态；保持单一渲染分支也避免悬停状态与行内确认互相干扰。
- 后续影响：同步修改 `文档/产品/04-原型交互说明.md` 的进行中任务行描述；任务页 UI 测试改为直接点击卡片操作；后续新增卡片操作时同样不得依赖悬停。

## 2026-10-12 F01 任务管理的领域校验边界

- 背景：F01 落地时需要明确三条规则在实现层的判定范围：持续任务开始日与「本机今日」的关系、目标追加的前置状态、以及同一操作标识在本地是否去重。
- 决策：① 持续任务「开始日不早于本机今日」只在该字段被新增或改动时校验，未改动的历史开始日不阻塞改名或调整计时配置；② 目标追加要求当前处于达标状态（待办按计划完成、持续任务今日达标），未达标返回 `appendNotAllowed`；③ 目标追加在本地按 `operationId` 去重，同步队列中已存在同一标识时返回 `isReplay` 结果且不再次修改目标。
- 备选方案：每次编辑都要求开始日不早于本机今日；允许未达标时提前提高目标；只依赖界面禁用按钮防止重复提交。
- 原因：逐字段校验避免历史计划周期被本机日期锁死；追加前置条件与 UC-12、UC-13 的前置条件保持一致，避免出现「未达标也能提高目标」的未定义路径；本地去重使连点或重试不会重复增加目标，与 BR-TASK-08 的幂等要求一致。
- 后续影响：F01 决策表新增 F01-D07、F01-D08、F01-D09；F02 实现会话保存后需要复核 `completionSource = .auto` 的写入路径；云端仍必须按 `operation_id` 独立实现幂等。

## 2026-10-13 本地开发分支使用任务卡承载中文说明

- 背景：AI 开发分支需要同时支持快速识别、完整中文说明、文档追踪和人工验收，但 Git 本地分支描述不会随提交或分支共享，单靠英文分支名也无法完整表达开发范围和 Bug 上下文。
- 决策：每个可独立开发、验证和合并的任务使用独立本地分支，名称采用 `foc-<任务卡生成AI>-<功能编号>-<流水号>-<分支类型>-<内容描述>`；分支名中的 AI 只表示任务卡初稿生成者，实际开发可以交给任意 AI 并在任务卡中单独记录。`F00` 与 `chore` 用于不归属具体产品功能的工程维护。每个新分支在创建前绑定一张已确认的中文任务卡，由任务卡记录完整说明、目标与非目标、相关产品和架构文档、验收标准及验证命令。`文档/AI开发/任务卡/README.md` 统一维护流水号、分支、任务卡和状态索引。当前不配置 Git 远程，不执行拉取、推送，不创建远程分支或 Pull Request。
- 备选方案：只通过较长的中文或英文分支名说明范围；使用 `git branch --edit-description` 保存分支备注；在提交信息或聊天记录中临时描述任务。
- 原因：任务卡可以随仓库共享和审查，并与现有 AI 交付流程直接衔接；短分支名便于命令行操作；集中索引可以在分支删除后继续保留流水号和任务历史，避免编号复用。
- 后续影响：新任务必须先确认任务卡和文档链接，再登记流水号并创建本地分支；更换开发执行者时更新任务卡，不修改分支名。开发 AI 完成自动化验证且通过 Codex 审查后提交到本地开发分支。人工功能与表现验收通过只表示具备合并条件，只有用户明确发出合并请求后 AI 才能合并 `main`；建立本规则前完成的历史任务卡不补编分支编号。未来如需远程协作，必须先新增决策并同步更新项目规则。

## 2026-10-13 任务卡生成 AI 与开发执行者分离

- 背景：任务卡的生成承担范围定义和交接责任，但实际编码可能根据任务类型、模型能力和成本交给不同 AI；把两者都写成「开发工具」会导致分支名与真实执行过程不一致。
- 决策：分支名中的 AI 标识记录任务卡初稿生成者，任务卡正文记录当前开发执行者及模型。任务卡可以由 DeepSeek、ChatGPT/Codex 或其他 AI 生成，开发任务也可以交给任意 AI；生成者或执行者都必须遵守已审核设计、停止条件、Codex 审查和人工验收规则。
- 备选方案：分支名记录第一个开发执行者；每次更换执行者都重命名分支；继续固定 OpenCode 为唯一开发执行者。
- 原因：任务卡是分支范围的正式来源，其生成者在分支创建时已经确定且稳定；执行者是可变的运行信息，放在任务卡中更准确，也不会因交接破坏分支标识。
- 后续影响：分支命名字段改为「任务卡生成 AI」；任务卡模板同时保留「任务卡生成 AI」和「当前开发执行者」；AI 开发流程与相关技能不再把 OpenCode 写成唯一执行者。

## 2026-10-13 规则类文档的聊天修改请求包含本地提交授权

- 背景：通用规则和流程文档已经在 AI 聊天中逐项讨论与确认，修改完成后再次询问是否创建本地提交会形成重复确认；产品相关改动则仍需要人工核对具体行为和影响。
- 决策：用户在当前聊天中要求新增或修改不改变产品行为的通用规则类文档，即同时授权 AI 在内容检查和 Codex 审查通过后直接创建本地提交，无需二次确认。产品需求与行为、业务规则、原型、功能设计、架构与接口、数据语义、测试场景与验收预期、功能任务卡及其实现仍须在本地正式提交前取得人工明确确认。混合改动按产品相关处理。
- 备选方案：所有改动提交前都再次询问；所有文档改动都自动提交；仅按文件目录判断是否需要人工确认。
- 原因：通用规则的修改请求本身已经表达提交意图，重复确认增加流程成本；产品与架构内容会直接约束用户体验和实现，仅凭目录无法准确判断风险，保留人工确认可以维持技术控制力。
- 后续影响：`AGENTS.md` 和 AI 开发流程增加本地提交授权边界。直接提交只适用于本地开发分支，不替代人工验收，也不构成合并 `main` 的授权。
