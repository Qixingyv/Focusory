# AI 开发流程

## 角色分工

- ChatGPT/Codex 负责设计：澄清需求，维护产品基线和 IBM 4+1 视图，确定接口契约，拆分任务并编写验收标准。
- OpenCode 负责开发：通过本地 Ollama `qwen3-coder:30b` 读取已确认的设计和任务卡，修改代码、补充测试并执行验证。
- ChatGPT/Codex 负责验收：审查 OpenCode 的代码差异、测试结果、产品正确性和文档一致性，并决定通过、返工或进入下一任务。
- OpenCode 遇到需求歧义、文档冲突、接口缺失或任务范围需要扩大时停止实现，不自行补充产品和架构决策。

## 推荐流程

1. 先在「番茄钟原型初版」中定位目标页面、状态和交互路径。
2. 在 `文档/产品/02-用户故事.md` 中确认成功流程、失败分支、编号化业务规则和验收标准。
3. 在 `文档/产品/功能/README.md` 中确认所属功能，并核对对应功能文档和主流程图。
4. 检查逻辑、开发、过程和物理视图是否已覆盖该用例。
5. 让 ChatGPT/Codex 阅读相关文档和现有代码，识别最小可实现范围，并先完成需要调整的产品与架构设计。
6. 由 ChatGPT/Codex 生成可独立实现的中文任务卡，明确分支信息、目标、非目标、前置阅读、影响模块、接口约束、实现步骤、验收标准、验证命令和相关文档链接。
7. 在 `文档/AI开发/任务卡/README.md` 中登记任务卡，确认功能内下一个未使用的流水号，并按根目录 `AGENTS.md` 的命名规则从最新 `main` 创建独立开发分支。
8. 将一张已确认的任务卡交给开发 AI；开发 AI 完成代码和测试，不重新解释或扩大设计范围。发现任务范围需要变化时停止实现，先交回 ChatGPT/Codex 更新任务卡和相关基线文档。
9. 开发 AI 运行与改动风险匹配的单元、集成、构建或 UI 测试，并报告修改文件、验证结果、遗留问题和风险。
10. 新增或修改用户可见文案时，检查 String Catalog、类型安全资源符号、翻译上下文、动态格式和稳定的 UI 测试标识。
11. ChatGPT/Codex 审查代码差异、测试结果、功能文档、流程图和受影响的 4+1 视图；未通过则退回原分支修改，通过后由 AI 在本地开发分支创建正式提交。
12. 人工对照任务卡和原型执行功能、交互和视觉验收；文案改动额外使用非本地化字符串或伪语言检查漏抽取、截断和布局适配。未通过则退回原分支修改、测试、审查和提交。
13. 人工验收通过后，将任务状态更新为已验收并等待用户明确发出合并请求；验收通过本身不构成合并授权，AI 不得自行合并。收到用户合并请求后，才将开发分支合并到 `main`，同步任务卡索引状态并删除已合并分支。

## 每次任务建议提供的信息

- 目标。
- 非目标。
- 前置阅读。
- 涉及文件或模块。
- 接口和架构约束。
- 建议实现步骤。
- 不希望改动的范围。
- 验收标准。
- 需要运行的验证命令。
- 对应的原型页面、状态或路径。
- 完整分支名称、中文说明和对应文档链接。

## 基线规则

- 当前界面、业务、API、数据和学习任务都以 2026-08-26 「番茄钟原型初版」为基线。
- 原型未包含的功能不通过旧文档自动恢复；需要新用例和新原型后才实现。
- 变更原型行为时，先更新用例视图，再同步检查其他 IBM 4+1 视图。
- macOS 用户可见文案统一维护在 `Focusory/Focusory/Resources/Localization/Localizable.xcstrings`；领域对象、API 字段和 UI 测试选择器不得依赖具体语言文案。

## 可复用提示词

### ChatGPT/Codex 设计与任务拆分

```text
请阅读相关产品文档、IBM 4+1 视图和现有代码，完成【功能名称】的设计与任务拆分。
你负责需求澄清、产品边界、接口契约和验收标准，不直接开始编码。
请先指出需要更新的产品与架构文档，再输出按依赖排序、可独立实现和验证的任务卡。
每张任务卡必须包含：分支信息、完整中文说明、相关文档链接、目标、非目标、前置阅读、影响模块、接口约束、实现步骤、验收标准和验证命令。
```

### OpenCode 实现任务

```text
请先阅读根目录 AGENTS.md、指定任务卡、相关文档和代码，然后只实现这张任务卡。
约束：
- 以已确认的任务卡、当前产品文档和架构文档为基线。
- 开始实现前确认当前分支名称与任务卡一致。
- 不改变产品需求、业务规则、架构基线、接口契约或任务范围。
- 发现歧义、冲突或缺失设计时停止实现并报告，不自行决定。
- 保持改动小而聚焦。
- 不新增生产依赖，除非先说明理由。
- 完成后运行任务卡指定的验证命令。
- 最终报告修改文件、验证结果、未解决问题和潜在风险。
```

### 代码审查

```text
请以 code review 视角检查当前改动。
优先指出相对当前交互原型的产品回归、bug、前后端契约偏移、缺失测试和时间/日期边界。
请给出文件和行号。
```

### 解释代码

```text
请解释【文件/模块】的职责、主要流程和关键函数。
请指出我后续修改时最需要注意的地方。
```
