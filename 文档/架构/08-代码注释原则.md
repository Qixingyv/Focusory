# Focusory macOS 代码注释原则

## 1. 目的与范围

本文规定 Focusory macOS 客户端 Swift、SwiftUI 和测试代码的注释方式。目标只有一个：注释用最短的文字补足代码无法表达的信息，让调用者理解契约、让维护者理解原因，不逐行翻译代码。

本文不规定 Python 文档字符串；后端进入实现阶段后按 Python 工具链另行补充。

## 2. 核心原则

- 先让代码自解释：优先用准确命名和短函数表达「做什么」，注释只补「为什么」和「调用者必须遵守什么」。
- 描述稳定契约，不复述实现步骤；注释随代码在同一变更中维护。
- 注释保持最短，能一句话说清就不写段落；不重复类型名、函数名或变量名已经表达的信息。

## 3. 三类注释规范

### 3.1 变量：说明代表什么

所有成员变量和计算属性都在声明正上方用一句 `///`，用最短的字说明其作用。只写语义，不重复名称和类型。

```swift
/// 当前在任务列表中被选中的任务标识。
@State private var selectedTaskID: FocusTask.ID?

/// 表示新建任务编辑器是否正在显示。
@State private var isNewTaskEditorPresented = false
```

局部临时变量优先靠清晰命名；只有来源、单位、生命周期或业务约束不明显时，才在声明前用一句 `//` 说明。

### 3.2 方法：说明作用与必要的入参、出参、特殊事项

所有函数和初始化器（含私有辅助函数、协议实现、生命周期方法和测试函数）都在声明正上方用一句 `///`，最简短说明作用。入参、出参、特殊说明仅在非显然时补充，用最简短的话：

- 入参：单位、合法范围或特殊值不明显时。
- 出参：含义无法由类型和名称完全表达时。
- 特殊事项：并发、事务、失败、副作用、复杂度等无法从签名看出时。

```swift
/// 返回指定状态的任务，保持原有顺序。O(n)。
func tasks(with status: FocusTaskStatus) -> [FocusTask]
```

```swift
/// 完成当前专注轮次并原子保存会话与任务进度；通知在事务成功后发送。
/// - 失败：计时不存在、状态不允许或本地事务失败时抛稳定业务错误。
func completeFocus(timerID: UUID, completedAt: Date) throws -> FocusSession
```

`throws` 接口在触发条件和调用方可依赖的错误不明显时，用一句话说明；不要只写「失败时抛出错误」。

### 3.3 类/结构/枚举：说明作用及特殊事项

类型在声明正上方用一句 `///`，最简单说明作用；有特殊事项（终态不可恢复、全局唯一、并发约束等）时补一句。

```swift
/// 显示并编辑任务基本信息与专注配置的弹窗。
struct TaskEditorSheet: View { ... }

/// 任务整体状态；`completed` 与 `abandoned` 为不可恢复的终态。
enum FocusTaskStatus: String, CaseIterable, Identifiable { ... }
```

UI 组件（`View`、`ViewModifier`、`ButtonStyle`、`ToggleStyle` 及 AppKit 桥接组件）同样一句 `///` 说明界面职责，不枚举内部视图层级、尺寸或颜色。

## 4. 实现注释 `//`

`//` 只解释局部实现背后的非显然原因：业务不变条件、Actor/线程/事务约束、时间与跨日归属、平台变通方案、算法关键不变式。放在所解释代码之前，靠近对应逻辑。

```swift
// 跨零点会话按结束时的本机日期归属，并同时固化当时的 IANA 时区。
let localDate = calendarProvider.localDate(at: endedAt)
```

## 5. 状态属性命名

`@State`、`@StateObject`、`@ObservedObject`、`@Environment`、`@EnvironmentObject`、`@Binding`、`@Published`、`@AppStorage`、`@FocusState`、`@FetchRequest` 和 `@Query` 等状态属性必须见名知意。

- 名称同时表达业务对象和状态含义，例如 `selectedTaskID`、`isTaskEditorPresented`。
- 布尔状态优先用 `is`、`has`、`can`、`should` 等判断语义前缀。
- 禁止 `flag`、`value`、`data`、`tmp`、`vm` 等脱离上下文无法理解的名称。

## 6. `MARK`、`TODO`、`FIXME`

- 同一类型存在三个以上清晰职责分区时使用 `// MARK:`，标题描述代码角色。
- `TODO` 表示已明确但未完成的后续工作，`FIXME` 表示已知的不正确行为或临时实现；内容必须具体、可搜索、可验收，已有任务编号时附上。
- 影响正确性、数据安全或用户数据的 `FIXME` 不得作为普通技术债静默合并。

```swift
// TODO(F06): 持久化同步游标后移除内存回退路径。
// FIXME(#142): macOS 26.4 恢复窗口时可能重复注册通知；升级最低版本后复核。
```

## 7. 文件头与本地化资源

- 不要求保留 Xcode 自动生成的「文件名 / target / Created by / 日期」头部；版本控制已记录作者与历史。
- 本地化资源注释说明 UI 场景、占位符含义、语气和长度限制，不重复源字符串。

## 8. 禁止事项

- 不写与代码同义的逐行注释；不给简单 getter/setter 或显然的枚举 case 加噪声注释。
- 不保留被注释掉的旧代码；需要时从 Git 历史恢复。
- 不在注释中记录密钥、令牌、真实用户数据、内部凭据或个人绝对路径。
- 不用注释掩盖含糊命名、过长函数或错误的模块边界；不复制需求全文到源码。
- 不承诺实现无法保证的性能、线程安全、顺序或错误类型。
- 不使用「临时」「以后修复」「神奇代码」等无法追踪验收的表述。

## 9. 代码审查清单

- [ ] 每个类型是否都有一句说明作用（及特殊事项）的 `///`。
- [ ] 每个函数/初始化器是否都有一句说明作用（及必要入参/出参/特殊事项）的 `///`。
- [ ] 每个成员变量和计算属性是否都有一句说明含义的 `///`。
- [ ] 状态属性是否在见名知意的同时有注释。
- [ ] 注释是否解释意图与约束，而不是复述代码。
- [ ] 并发、事务、失败、时间归属等非显然语义是否用最短的话点明。
- [ ] `TODO`/`FIXME` 是否具体、可搜索、可验收。
- [ ] 是否删除了失效注释和被注释掉的旧实现。

## 10. 最小采用策略

本原则从新代码和正在修改的代码开始执行；类型、函数和成员变量注释是强制基线，存量代码在被触达时同步补齐。最终标准是：调用者能理解契约，维护者能理解原因，注释与代码保持一致。
